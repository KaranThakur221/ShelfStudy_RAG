Software Project Report

StudyShelf

A local-first exam preparation workspace for faculty PDFs, grounded answers, exam responses, and source-backed quizzes.
Project character
StudyShelf combines local document storage, CPU-based semantic indexing, and an API-only cloud generation layer. The result is a focused personal study environment in which uploaded course material remains on the user's device.
Repository: RAG / StudyShelf
Scope: Implemented features, architecture, interfaces, operations, testing, security, and limitations
01 · Overview

Executive summary

StudyShelf is a local-first Retrieval-Augmented Generation (RAG) application designed for exam preparation. It accepts selectable-text PDFs, extracts and chunks their content, creates local semantic embeddings, stores vectors in a persistent ChromaDB collection, and retrieves relevant passages for answer and quiz generation.

The web interface is a React/Vite single-page application. The backend is a FastAPI service that owns file handling, indexing, retrieval, model calls, validation, and source citation. The OpenAI API is used only from the backend for generated responses; the local embedding model runs on CPU.

Primary value proposition

  • Turn scattered faculty notes into a searchable personal study library.
  • Answer questions from retrieved course excerpts instead of unsupported general knowledge.
  • Use source IDs and page metadata to trace generated claims to the original PDF.
  • Generate exam-ready answers with 2-, 5-, and 10-mark response formats.
  • Practice with validated multiple-choice quizzes and explanations.
Design boundary: upload and indexing are intended to be local operations. Generation requires a configured OpenAI API key and network access, but the key is never sent to the frontend.

Supported document metadata

Each PDF can carry optional subject, semester, unit, and document_type metadata. These values are stored in the manifest and copied to vector metadata so filters affect retrieval as well as library presentation.

03 · Architecture

System architecture and data flow

React/Vite UI
127.0.0.1:5173→FastAPI API
127.0.0.1:8000→Services
PDF · chunks · retrieval · LLM

Persistent local state: data/uploads/ and data/chroma/

Ingestion path

  1. The frontend submits a multipart PDF and optional classification fields.
  2. The API checks the extension, applies the configurable maximum upload size, and passes bytes to the document service.
  3. PyMuPDF extracts text page by page while preserving 1-based page numbers. Encrypted, empty, invalid, and non-selectable-text PDFs are rejected with actionable errors.
  4. The chunking service splits page text by words using configurable CHUNK_SIZE and CHUNK_OVERLAP.
  5. A SHA-256 content hash detects duplicate PDFs before another index is created.
  6. sentence-transformers/all-MiniLM-L6-v2 embeds chunks on CPU with normalized vectors.
  7. ChromaDB persists chunk IDs, text, embeddings, page metadata, and classification metadata. The original PDF and manifest entry are then saved.

Question and generation path

  1. A question/topic is validated by Pydantic and optionally scoped by subject and unit.
  2. The query is embedded locally and used to retrieve the configured top-k passages from ChromaDB.
  3. Retrieved passages become numbered evidence blocks such as [S1], with filename and page context.
  4. The backend sends instructions and evidence to the OpenAI Responses API. The prompt treats excerpts as untrusted data and requires evidence-only answers.
  5. Citations are normalized to allowed source IDs. Unknown source IDs and fabricated page details are removed.
  6. The API returns the generated answer/questions plus structured source objects for the UI.

Validation and response guarantees

  • Questions and topics have minimum and maximum lengths.
  • Top-k is bounded to 1–20; quiz count is bounded to 1–15.
  • Exam marks are a closed set: 2, 5, or 10.
  • Quiz questions require exactly four non-empty options and a correct index from 0 to 3.
  • Unknown citation IDs are removed rather than presented as trusted references.

Example request

curl -X POST http://127.0.0.1:8000/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"question":"Explain AVL tree balancing","subject":"Data Structures","unit":"Unit 3"}'
06 · Frontend

User experience and interaction model

The frontend is a compact React 19 application bundled by Vite. Its visual system uses a warm neutral canvas, terracotta accent, compact typography, icon-based navigation, cards, and responsive sidebar behavior. API calls are centralized through a small request helper that converts non-2xx responses into visible error messages.

ScreenInteraction details
DashboardDisplays library summary, health/model state, recent documents, and shortcuts into upload, question answering, and quiz creation.
PDF LibrarySearches filenames, filters subjects/units, opens PDFs in a new tab, exposes metadata controls, confirms deletion, and reports duplicate/indexing results.
Ask your PDFsSubmits a question, shows generated answer, source previews, page references, and recent interaction history.

State and failure handling

  • Initial loading state and periodic refresh keep the library count and health indicator current.
  • Busy states guard actions while upload, chat, exam, or quiz requests are running.
  • Errors appear in a dismissible alert; successful upload/delete actions use transient toast feedback.
  • Mobile navigation opens as an overlay with a scrim and close control.
  • Source links target the original stored PDF and include a page anchor.

Recorded environment verification

The repository README records that frontend installation and npm run build passed in the supplied workspace. Python compilation, direct chunking checks, and PDF text validation also passed. Backend dependency installation, pytest execution, backend startup, and end-to-end checks were blocked by unavailable package/network dependencies and sandbox bind restrictions; these should be rerun in a network-enabled environment with Python 3.11 or 3.12.

Recommended release gate

  1. Create a Python 3.11 or 3.12 virtual environment and install the pinned backend requirements.
  2. Run backend/.venv/bin/python -m pytest backend/tests -q.
  3. Run cd frontend && npm run build.
  4. Start both services and perform the documented synthetic PDF upload, filtered question, exam answer, quiz, metadata update, and deletion smoke checks.
08 · Trust and operations

Security, privacy, and data management

Implemented safeguards

  • Both development servers bind to loopback addresses by default.
  • CORS is limited to the local Vite origins.
  • OpenAI credentials remain backend-only and the health endpoint exposes only a boolean configured state.
  • Uploaded filenames are normalized to a stored UUID-based filename; user filenames are not used as filesystem paths.
  • Upload size is bounded and PDF type is checked before indexing.
  • Evidence excerpts are explicitly treated as untrusted prompt data to reduce instruction injection from document text.
  • Model requests use a 45-second timeout and one retry, with user-safe error messages.
  • Generated data directories are ignored by Git; secrets and virtual environments are also ignored.

Backup and recovery

For a consistent backup, stop the application and copy both data/uploads/ and data/chroma/. The upload directory contains the original PDFs and a small documents.json manifest; the ChromaDB directory contains the persistent semantic index.

Operational startup

python3 -m venv backend/.venv
backend/.venv/bin/python -m pip install -r backend/requirements.txt
cd frontend && npm install && cd ..
cp backend/.env.example backend/.env
# set OPENAI_API_KEY in backend/.env
./scripts/start.sh

Manual alternative: start Uvicorn on port 8000 and Vite on port 5173. API documentation is available at http://127.0.0.1:8000/docs.

Prioritized next steps

  1. Release confidence: complete backend dependency installation and full test/smoke execution in a supported Python environment.
  2. Document coverage: add OCR and structure-aware extraction for real-world course materials.
  3. Answer quality: add retrieval thresholds, reranking, and a small grounded-answer evaluation set.
  4. Deployment readiness: add authentication, secure configuration, production CORS/TLS, logging, and backup automation.
  5. Performance: measure indexing time, embedding memory, retrieval latency, and generation latency as the library grows.
